# The world is simulated in each browser and relayed as presence

The rooftop is a toy, not the game: walking, jumping, standing on heads, shoving and falling never change who guessed what. So each browser owns its own character. `@guess/world` (pure TypeScript, `bun test`) steps that character against the platforms and against the last known positions of everyone else, and the browser sends its state (position, velocity, facing, animation) about fifteen times a second. The host relays it to the other sockets outside the room state, as trucossoca relays presence, keeping only the latest per sender between sends. Others' bodies are drawn interpolated between the last two states received. A shove is a message from the shover to the pushed person's browser, which applies the knockback to itself; whoever is pushed decides where they land.

## Considered options

- **Server-authoritative physics**: the server steps every body at a fixed rate and sends positions back. Fair and consistent, but every jump would wait a round trip, the server would run a game loop for a toy, and nothing in the game depends on fairness here.
- **Peer-to-peer (WebRTC)**: lower latency between friends, but signalling, NAT traversal and a second transport for a few dozen bytes a second.

## Consequences

Two screens can disagree for a moment about who stood where, and a modified client can fly; neither matters, because falling has no effect on the game. Collision against remote bodies uses positions up to ~70 ms old, so pushing through a crowd feels slightly soft, which is fine for a party game. Presence is not activity: a room where people only walk around still dies after ten minutes. The world package has no knowledge of rooms, sockets or Pixi, so its rules (gravity, solid bodies, riding on a head, shove knockback, respawn) are tested headless.

## Amendment: the server simulates the funny bots

"Funny bots" (issue #55) are characters nobody controls that show up on the roof while the game runs, to distract and amuse. Someone has to own their bodies so every screen sees the same thing, and no browser is always there, so the server does: while the option is on and the game is playing, `RoomHost` runs a loop (30 steps a second) over `BotWorld` (`apps/server/src/bots.ts`), which steps each bot with the same `@guess/world` physics the browsers use. Each bot's presence goes out as an ordinary `presence` message with a `b…` id, at the players' rate and only when it changed; the room snapshot carries the list of bots on the roof (`bots`), so a client draws them exactly as it draws a person. A player's shove on a bot is applied by the server; a bot's shove on a player is a `shoved` message, applied by that player's browser as always.

This is the game loop on the server that the original decision avoided. It is acceptable here because it exists only while the option is on and a game is running, it steps at most fifteen bodies, and nothing in the guessing depends on it: the bots know nothing about turns, votes or the clock. Players are still simulated in their own browsers; the bots see them through the last presence each one sent.

The behaviour is in two layers, both random on purpose so players can't predict it: a director with a wandering mood decides when and how many arrive (from none to fifteen, tending to get busier in a long game but on no schedule), and each bot scores what it could do now by its own random personality and what is around it, then draws among the best. The server takes each character's attack length from `apps/server/src/attacks.json`, written by `bun run sprites`, because the production image doesn't carry the client's atlases.

A rare director event is the boss (issue #60): one giant bot at a time that takes six shoves to knock off. The server only says how big it is (`scale` on its entry in `bots`; absent means 1, so clients and servers from before it still agree); drawing it bigger is the client's job. Its body is taller and wider for everyone else (`h` and `wide` on `Other` in `@guess/world`), never deeper, so nobody stands inside the drawing and there is always a way around it.

## Amendment: limits, and presence as activity while a game runs

An audit (issue #72) found that trusting each browser this much let one socket freeze the server: every shove ran a full room `step()` just to count a stat, and nothing limited how often a socket could ask for anything. The world stays in the browsers, but the host now checks what it relays:

- Every client message except presence spends a token from a per-socket bucket (40 at once, 20 a second); past that it is dropped, and a socket that keeps going is closed with `4429` (`CLOSE_TOO_MANY`), which the client explains instead of reconnecting. Presence (about 15 a second from a tab) only counts against a much wider bucket for every message (120 at once, 60 a second), checked before parsing, so a presence flood is cut off too.
- A shove only goes out at the shove's own pace (`SHOVE_COOLDOWN_MS` minus 150 ms for the network; the targets of one swing arrive together) and only if the target is within reach of the shover by their last presences (`inShoveReach`, the reach plus slack for presences up to ~100 ms stale). The pushed browser ignores a shove while it is already stunned, fallen or blinking back.
- Stats are plain counters in `RoomHost`, written into the room state before each room step while the game runs, so the end snapshot still carries them. A fall is the presence dropping below `FALL_Y`, at most once per `RESPAWN_MS`; it no longer depends on `blink`, which stays on when someone falls again while still blinking from the last respawn.

The consequence above said presence is not activity, so a room where people only walk around dies after ten minutes. That still holds in the lobby, but during a game it killed rooms whose players were busy talking and fooling around on the roof. So while the game is playing, a member's presence counts as activity, at most once a minute (the host sends the room an `alive` input, which never produces a snapshot), and so does the game moving on by itself (the turn changing, a vote opening or closing, someone guessing or giving up). A tab left in the background sends no presence (the frame loop stops), so a forgotten game still dies once its turns stop moving. To keep a background tab's seat, the server tolerates 90 s of silence instead of 30, and the client pings from a Worker, whose timers the browser does not throttle like a hidden page's.

## Amendment: the bots talk

Some funny bots now talk, in the same chat bubbles people use: the server sends an ordinary `chat` message with the bot's `b…` id, and the client already draws a bubble over any head with that id, so nothing changed on the wire or in the client. Lines come from a language model on Groq; there are no canned lines, and without `GROQ_API_KEY` in the server's environment (or with the budget spent) the bots are simply silent. Setup, model and numbers are in `docs/groq.md`.

This overrides "the bots know nothing about turns, votes or the clock" above, for talking only (how they move is unchanged). To be funny a bot needs to know where it is, so each request carries the bot's persona (`apps/server/src/personas.ts`, one per character, researched from each character's source) and the scene: whose turn it is, an open vote, who has already guessed or given up, who is near and which character they play, what just happened (a shove, a fall, a guess, the boss landing) and the recent chat. **Post-its never go to the model**, nor anything derived from them, because naming someone's post-it would spoil the game: the scene is built from nicknames, characters, positions and ranking only; chat that mentions a post-it reaches the model with those words masked (`redact`); and a model line that contains a post-it word is dropped (`leaks`), like one that trips the content filter (`unsafe`). Player chat itself does go to Groq; the owner accepted that.

Where it lives follows the room's split between pure logic and I/O. The **talk brain** (`TalkBrain`, `apps/server/src/talk.ts`) is pure and unit-tested: when a bot arrives it rolls whether it talks (30%, bosses included), it turns what the host tells it (chat, shoves, falls, the game moving on, the roster) into a bot's **wish to talk**, it decides which wish goes out now and builds the prompt, and it cleans or discards the answer (late, bot gone, game over, conversation moved on, unsafe, leaking). `RoomHost` feeds it from what already passes through it, asks it once per bot step, sends the request to the injected `Talker` without waiting, and turns an accepted answer into a `chat` message. The `Talker` (`apps/server/src/groq.ts`) is one per process, because Groq's free limits are per account: its budget counts requests and tokens per minute and per day for every room together, keeps headroom below each limit, reserves the last part of each window for replies to people over reactions and reactions over idle chatter, and obeys Groq's rate-limit headers and 429s. Each room also caps itself (one request in flight, about two a minute, per-bot gaps, bots answering each other at most three lines in a row).

Considered: canned lines as a fallback (rejected by the owner: everything comes from the model, or nothing); calling the model from the browser (would expose the key and multiply the requests by the number of tabs); a bigger model (slower and with tighter free limits, for one-line jokes).
